# Security Notes

Этот проект работает с внешними сайтами, локальной базой данных и экспортами, поэтому базовая безопасность строится вокруг четырёх принципов:

1. не доверять внешнему контенту;
2. не хранить секреты в репозитории;
3. разделять код, runtime-данные и generated-отчёты;
4. не выполнять никаких действий на основе непроверенного контента.

## Что считается чувствительным

В репозиторий нельзя коммитить:

- `.env` и любые `.env.*`;
- API-ключи и токены;
- локальные базы данных;
- generated `CSV/XLSX` отчёты;
- временные browser / pytest артефакты;
- логи с потенциальными заголовками авторизации.

## Где должны храниться секреты

Секреты читаются только из переменных окружения.

Примеры:

- `GIGACHAT_AUTH_KEY`
- будущие Telegram / Sheets / email credentials

Если ключ однажды оказался в переписке, скриншоте или git history, его нужно считать скомпрометированным и перевыпустить.

## Работа с внешними сайтами

Проект ходит на внешние сайты и может скачивать книги для подтверждения публикации. Из этого следуют ограничения:

- разрешены только `http` и `https` URL;
- скачанные файлы не исполняются;
- браузерный fallback используется только как способ скачать файл;
- временные browser-артефакты не должны попадать в git;
- при невозможности корректно подтвердить публикацию проект должен ошибаться честно, а не выдумывать результат.

## Runtime-данные

Локально проект использует несколько зон:

- `data/` — локальная БД;
- `reports/` — generated аналитические отчёты;
- `output/` — старые generated артефакты и временные материалы;
- `tmp/` и `tests_tmp/` — временные данные тестов и локальных проверок.

Ни одна из этих директорий не является исходным кодом проекта.

## Репозиторная гигиена

Перед публикацией и перед push полезно запускать:

```bash
python scripts/repo_security_check.py
```

Скрипт проверяет:

- нет ли `.env` и похожих файлов;
- нет ли баз данных и generated-отчётов в индексируемой зоне;
- нет ли строк, похожих на захардкоженные токены и заголовки авторизации.

## Что проект сознательно не делает

- не хранит секреты в коде;
- не даёт LLM прямой доступ к данным;
- не выполняет скачанный контент;
- не делает write-операции по внешним данным автоматически.

## Практический чеклист

Перед GitHub:

1. проверить `.gitignore`;
2. проверить, что `data/monitor.db` не попадает в commit;
3. проверить, что `reports/` и `output/` не попадают в commit;
4. запустить `python scripts/repo_security_check.py`;
5. убедиться, что примеры данных обезличены.
